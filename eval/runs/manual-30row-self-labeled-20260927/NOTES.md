# What this eval run actually is (read before `report.md`)

`report.md` in this directory was generated by the project's own real evaluation statistics
machinery (`eval/run.py:run_eval` — the same agreement/selective-prediction/FP-FN/confusion-
matrix/failure-mode code a real sealed eval would use), fed with real data:

- Real, licensed Wikimedia Commons product photos, run through the actual live Gemini
  judgment pipeline and the actual deterministic disposition engine
  (`agent/manual_test_images/returns_input_30.csv` / `returns_output_30.csv`).
- 30 units across 8 distinct products and all 6 category policies.

`report.md`'s own header says "(sealed eval)" — **that line is generic boilerplate the
renderer prints whenever `dev_mini=False`, and it is misleading here.** This is not the
sealed eval `RULES.md` describes. Specifically:

1. **Single labeller, not two independent ones.** The "gold" label and both "human_a"/
   "human_b" labels in this run are the same person (the author, who also designed the test
   scenarios) — not two people independently judging the photos blind to what each row was
   built to demonstrate. Every "labeller_a_vs_b" agreement statistic in `report.md` is
   therefore 1.000 by construction, not evidence of real inter-rater agreement — it should be
   read as proof the *statistics code* works, exactly the way the `--dev-mini` run's
   equivalent numbers should be read.
2. **30 units, not the required ≥50.**
3. **Designer-set ground truth, not blind labelling.** Gold labels come from knowing what
   each row was built to show (e.g. "this row's returned photo is deliberately a different
   product"), not from a human independently examining the photo without that context.
4. **The "identity" check measures the wrong signal for this dataset — logged as finding
   F-024** (`build-log.md`). The batch tool's `identity_match` output column is the
   before-file's value carried forward unchanged (correct, by design — it's never
   re-derived by the agent), not the model's own read of the *returned* photo. On the 3
   deliberate identity-mismatch rows, this column still reads `yes` because that's what the
   seller recorded at sale time. The three "identity disagreements" `report.md` shows
   (`UNIT-AIR-02`, `UNIT-LEASH-02`, `UNIT-SHAMPOO-02`) are an artifact of that column choice,
   not a vision failure — the disposition itself was safe on all three (`pending_review`,
   never `restock`/`refurbish`), because the deterministic engine's R03 gate uses the
   model's actual internal identity judgment, not this pass-through column. Read the
   `condition`/`completeness`/`disposition` numbers as the more meaningful signal from this
   run; discount the `identity` agreement numbers for the reason above.
5. **Condition grades are the author's own single-pass estimate, not rubric-graded.** These
   are real product photos, not staged used-condition returns with independently verified
   wear — "Used - Like New" vs "Used - Very Good" etc. was judged once, by one person,
   without cross-checking against the Amazon condition rubric line by line.

## What's genuinely real about it

- Every photo is real and public; every model call was a real, live Gemini Interactions API
  call (not mocked) at the time each row succeeded; every disposition came from the real
  deterministic rules engine.
- `completeness` (70% raw agreement, 90% coverage) and `disposition` failure-mode counts
  (`condition_ambiguity` on 12/30 rows — the model declining to commit to a grade from a
  single stock photo, `false_missing_component` on 4 rows, `wrong_disposition` on 3 baseline
  rows where the engine chose `refurbish` over the author's guessed `restock`) are real,
  measured, reproducible numbers from real runs — not fabricated to look good. One `dispose`→
  `restock` disagreement (`UNIT-SHAMPOO-01`) is flagged in `report.md`'s "dangerous" row;
  read footnote 5 above before treating it as a safety bug rather than a labelling
  uncertainty.
- 10 of the 30 rows never reached a live model call at all (6 by deliberate design — no
  photo, unknown/blank category; 4 from real API quota exhaustion encountered while building
  this dataset) and are excluded from `condition`/`disposition` scoring accordingly — see
  `per_unit_table.csv` and the source run logs for exactly which and why.

## What a real, RULES.md-compliant eval still needs

- A genuine sealed set of ≥50 units the agent has never been tuned against.
- Two people who did not design the test cases, independently labelling each unit blind to
  each other's answers, with a documented tie-break process for disagreements.
- The batch tool (or the DB-backed pipeline) exposing the model's own identity verdict on
  the *returned* photo as its own field, not only the carried-forward catalog value (F-024).
